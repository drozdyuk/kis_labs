## 2. Теоретичні відомості

### 2.1. API як інтеграційний інтерфейс ERP

ERP-система в корпоративному ландшафті рідко працює ізольовано. Типове підприємство використовує десятки програмних систем, і ERP має обмінюватися з ними даними: приймати замовлення з інтернет-магазину, передавати рахунки у бухгалтерську систему, отримувати курси валют із зовнішнього сервісу.

Для цього ERP надає API — програмний інтерфейс, через який зовнішні системи можуть читати та змінювати дані. Odoo підтримує два протоколи зовнішнього доступу: XML-RPC та JSON-RPC. Обидва працюють поверх HTTP, не потребують спеціальних бібліотек і доступні з будь-якої мови програмування.

### 2.2. Протокол XML-RPC

XML-RPC — один із найпростіших протоколів віддаленого виклику процедур (Remote Procedure Call). Клієнт надсилає HTTP POST-запит із тілом у форматі XML, що містить назву методу та параметри. Сервер виконує метод і повертає результат у тому ж форматі.

Переваги XML-RPC: простота реалізації, підтримка у стандартній бібліотеці Python (`xmlrpc.client`), прозорість (запити можна читати та дебажити). Недолік: XML-обгортка додає накладні витрати порівняно з JSON-RPC, що стає помітним при великих обсягах даних.

### 2.3. Ендпоінти Odoo XML-RPC

Odoo надає три XML-RPC ендпоінти:

**`/xmlrpc/2/common`** — службовий ендпоінт. Використовується для автентифікації (`authenticate`) та отримання інформації про сервер (`version`). Не потребує попередньої автентифікації.

**`/xmlrpc/2/object`** — основний робочий ендпоінт. Через метод `execute_kw` надає доступ до всіх моделей Odoo: пошук, читання, створення, оновлення, видалення записів. Потребує автентифікації (uid + пароль передаються в кожному запиті).

**`/xmlrpc/2/db`** — ендпоінт управління базами даних. Дозволяє створювати, видаляти, клонувати бази. У цій роботі не використовується.

### 2.4. Метод execute_kw

Усі операції з даними виконуються через один метод `execute_kw` з такою сигнатурою:

```
models.execute_kw(db, uid, password, model, method, args, kwargs)
```

Де:
- `db` — назва бази даних (наприклад, `erplab`);
- `uid` — ідентифікатор користувача (отриманий при автентифікації);
- `password` — пароль користувача;
- `model` — технічна назва моделі (наприклад, `edu.student`);
- `method` — назва ORM-методу (`search`, `read`, `create`, `write`, `unlink`);
- `args` — позиційні аргументи методу;
- `kwargs` — іменовані аргументи (необов'язкові).

Це той самий ORM, з яким ви працювали у ЛР2 через Python-код моделі, але тепер виклик іде ззовні через мережу.

### 2.5. Основні ORM-методи

| Метод | Призначення | args | Повертає |
|-------|-------------|------|----------|
| `search` | Пошук ID записів за доменним фільтром | `[domain]` | Список ID |
| `search_read` | Пошук + читання за один виклик | `[domain]` | Список словників |
| `read` | Читання записів за списком ID | `[ids]` | Список словників |
| `create` | Створення одного або кількох записів | `[values]` або `[list_of_values]` | ID або список ID |
| `write` | Оновлення записів | `[ids, values]` | True |
| `unlink` | Видалення записів | `[ids]` | True |
| `search_count` | Кількість записів за фільтром | `[domain]` | Ціле число |

**Доменний фільтр (domain)** — це список умов у форматі `[(field, operator, value)]`. Умови за замовчуванням об'єднуються через AND. Для OR використовується оператор `'|'` у польській (префіксній) нотації.

Приклади:
- `[('status', '=', 'studying')]` — студенти зі статусом «Навчається».
- `[('avg_grade', '>=', 90)]` — студенти з балом ≥ 90.
- `['|', ('group_code', '=', 'КН-51м'), ('group_code', '=', 'КН-52м')]` — студенти групи КН-51м АБО КН-52м.

### 2.6. ETL: Extract, Transform, Load

ETL — стандартний патерн інтеграції даних. Дані витягуються (Extract) із джерела (файл, база, API), трансформуються (Transform) у формат цільової системи (перейменування полів, перетворення типів, валідація), і завантажуються (Load) у цільову систему.

У контексті ERP типові ETL-сценарії: імпорт довідника контрагентів із бухгалтерської системи, завантаження прайс-листа постачальника, міграція даних зі старої системи при впровадженні ERP.

### 2.7. Серверні дії та заплановані дії

Окрім зовнішньої інтеграції, Odoo дозволяє автоматизувати логіку всередині системи.

**Серверна дія (Server Action)** — код Python, що виконується у відповідь на подію або вручну. Має доступ до `self` (поточний запис), `env` (середовище Odoo), `model` (поточна модель). Можна прив'язати до кнопки або до автоматизації.

**Запланована дія (Scheduled Action / Cron)** — серверна дія, що виконується автоматично за розкладом (наприклад, щодня о 02:00 або кожні 30 хвилин). В Odoo реалізована через модель `ir.cron`.

## 3. Підключення та автентифікація

### 3.1. Базовий скрипт підключення

Створіть на хост-машині (не всередині контейнера) файл `odoo_rpc.py`:

```python
import xmlrpc.client

# ---- Параметри підключення ----
URL = "http://localhost:8069"
DB = "erplab"          # назва вашої бази (може відрізнятися)
USERNAME = "admin"
PASSWORD = "admin"     # пароль адміністратора

# ---- Підключення до ендпоінтів ----
common = xmlrpc.client.ServerProxy(f"{URL}/xmlrpc/2/common")
models = xmlrpc.client.ServerProxy(f"{URL}/xmlrpc/2/object")

# ---- Перевірка з'єднання ----
server_version = common.version()
print(f"Odoo версія: {server_version['server_version']}")

# ---- Автентифікація ----
uid = common.authenticate(DB, USERNAME, PASSWORD, {})

if uid:
    print(f"Автентифікація успішна. UID = {uid}")
else:
    print("Помилка автентифікації. Перевірте логін, пароль та назву бази.")
    exit(1)
```

Запуск:

```bash
python3 odoo_rpc.py
```

Очікуваний результат:

```
Odoo версія: 19.0
Автентифікація успішна. UID = 2
```

Зверніть увагу: `uid` (User ID) — це числовий ідентифікатор користувача в Odoo. Для адміністратора зазвичай `uid = 2`. Цей ідентифікатор передається в кожному наступному запиті замість повторної автентифікації.

### 3.2. Винесення підключення у функцію

Для зручності подальшої роботи винесемо підключення у повторно використовувану функцію. Створіть файл `connection.py`:

```python
"""Модуль підключення до Odoo XML-RPC API."""

import xmlrpc.client

URL = "http://localhost:8069"
DB = "erplab"
USERNAME = "admin"
PASSWORD = "admin"


def connect():
    """
    Автентифікується та повертає (models, db, uid, password)
    для подальших викликів execute_kw.
    """
    common = xmlrpc.client.ServerProxy(f"{URL}/xmlrpc/2/common")
    models = xmlrpc.client.ServerProxy(f"{URL}/xmlrpc/2/object")

    uid = common.authenticate(DB, USERNAME, PASSWORD, {})
    if not uid:
        raise ConnectionError(
            "Автентифікація не вдалася. "
            "Перевірте URL, назву БД, логін та пароль."
        )

    return models, DB, uid, PASSWORD
```

Тепер у всіх подальших скриптах підключення займає один рядок:

```python
from connection import connect

models, db, uid, password = connect()
```

### 4.2. Пошук з фільтрами (domain)

Створіть файл `search_students.py`:

```python
"""Приклади доменних фільтрів для пошуку записів."""

from connection import connect

models, db, uid, password = connect()

MODEL = "edu.student"


def search_read(domain, fields=None):
    """Допоміжна функція: пошук + читання."""
    if fields is None:
        fields = ["name", "group_code", "avg_grade"]
    return models.execute_kw(
        db, uid, password, MODEL, "search_read",
        [domain],
        {"fields": fields}
    )


# Сценарій 1: студенти з балом >= 90
honors = search_read([("avg_grade", ">=", 90)])
print(f"Відмінники ({len(honors)} записів):")
for s in honors:
    print(f"  {s['name']} — {s['avg_grade']}")

# Сценарій 2: студенти певної групи
# (замініть 'КН-51м' на групу, що є у ваших тестових даних)
group = search_read([("group_code", "=", "КН-51м")])
print(f"\nГрупа КН-51м ({len(group)} записів):")
for s in group:
    print(f"  {s['name']}")

# Сценарій 3: OR-фільтр (дві групи)
two_groups = search_read([
    "|",
    ("group_code", "=", "КН-51м"),
    ("group_code", "=", "КН-52м"),
])
print(f"\nКН-51м або КН-52м ({len(two_groups)} записів):")
for s in two_groups:
    print(f"  {s['name']} ({s['group_code']})")

# Сценарій 4: пагінація (limit + offset)
page = models.execute_kw(
    db, uid, password, MODEL, "search_read",
    [[]],
    {"fields": ["name"], "limit": 3, "offset": 0, "order": "name asc"}
)
print(f"\nПерші 3 студенти (за алфавітом):")
for s in page:
    print(f"  {s['name']}")
```

## 5. Створення, оновлення та видалення (Create, Update, Delete)

### 5.1. Повний CRUD-цикл

Створіть файл `crud_demo.py`:

```python
"""Демонстрація повного CRUD-циклу через XML-RPC."""

from connection import connect

models, db, uid, password = connect()

MODEL = "edu.student"

# ==================================================
# CREATE — створення запису
# ==================================================
new_id = models.execute_kw(
    db, uid, password, MODEL, "create",
    [{"name": "Тестовий Студент", "group_code": "КН-00т", "avg_grade": 85.5}]
)
print(f"[CREATE] Створено запис ID = {new_id}")

# Перевірка: прочитаємо створений запис
created = models.execute_kw(
    db, uid, password, MODEL, "read",
    [[new_id]],
    {"fields": ["name", "group_code", "avg_grade", "is_honors"]}
)
print(f"  Дані: {created[0]}")
print(f"  is_honors = {created[0]['is_honors']} (очікуємо False, бо бал < 90)")

# ==================================================
# UPDATE — оновлення запису
# ==================================================
models.execute_kw(
    db, uid, password, MODEL, "write",
    [[new_id], {"avg_grade": 95.0}]
)
print(f"\n[UPDATE] Оновлено бал до 95.0 для ID = {new_id}")

# Перевірка: чи перерахувалося computed поле?
updated = models.execute_kw(
    db, uid, password, MODEL, "read",
    [[new_id]],
    {"fields": ["avg_grade", "is_honors"]}
)
print(f"  avg_grade = {updated[0]['avg_grade']}, is_honors = {updated[0]['is_honors']}")
print(f"  (очікуємо is_honors = True, бо бал >= 90)")

# ==================================================
# DELETE — видалення запису
# ==================================================
models.execute_kw(
    db, uid, password, MODEL, "unlink",
    [[new_id]]
)
print(f"\n[DELETE] Видалено запис ID = {new_id}")

# Перевірка: запис більше не існує
remaining = models.execute_kw(
    db, uid, password, MODEL, "search",
    [[("id", "=", new_id)]]
)
print(f"  Пошук видаленого ID: знайдено {len(remaining)} записів (очікуємо 0)")

print("\nCRUD-цикл завершено успішно.")
```

## 7. ETL-скрипт

### 7.1. Базова реалізація

Створіть файл `etl_import.py`:

```python
"""
ETL-скрипт: імпорт студентів з CSV у модель edu.student через XML-RPC.

Етапи:
  Extract  — читання CSV-файлу
  Transform — валідація, перетворення типів
  Load     — створення записів у Odoo
"""

import csv
import sys
from connection import connect

models, db, uid, password = connect()

MODEL = "edu.student"
CSV_FILE = "students_import.csv"

VALID_STATUSES = {"studying", "completed", "academic_leave"}


# ==================================================
# EXTRACT — читання CSV
# ==================================================
def extract(filepath):
    """Зчитує CSV і повертає список словників."""
    with open(filepath, encoding="utf-8") as f:
        reader = csv.DictReader(f)
        rows = list(reader)
    print(f"[Extract] Прочитано {len(rows)} рядків з {filepath}")
    return rows


# ==================================================
# TRANSFORM — валідація та перетворення
# ==================================================
def transform(rows):
    """
    Валідує та трансформує дані:
    - avg_grade: рядок → float, перевірка діапазону 0–100
    - status: перевірка допустимих значень
    - name, group_code: перевірка на непорожність
    """
    valid = []
    errors = []

    for i, row in enumerate(rows, start=2):  # start=2: рядок 1 — заголовок
        try:
            name = row["name"].strip()
            group_code = row["group_code"].strip()
            avg_grade = float(row["avg_grade"])
            status = row["status"].strip()

            if not name:
                raise ValueError("Порожнє ім'я")
            if not group_code:
                raise ValueError("Порожній код групи")
            if not (0 <= avg_grade <= 100):
                raise ValueError(f"Бал {avg_grade} поза діапазоном 0–100")
            if status not in VALID_STATUSES:
                raise ValueError(f"Невідомий статус: '{status}'")

            valid.append({
                "name": name,
                "group_code": group_code,
                "avg_grade": avg_grade,
                "status": status,
            })

        except (ValueError, KeyError) as e:
            errors.append(f"  Рядок {i}: {e}")

    print(f"[Transform] Валідних: {len(valid)}, з помилками: {len(errors)}")
    for err in errors:
        print(err)

    return valid


# ==================================================
# LOAD — завантаження у Odoo
# ==================================================
def load(records):
    """Створює записи в Odoo через XML-RPC."""
    if not records:
        print("[Load] Немає записів для завантаження.")
        return []

    new_ids = models.execute_kw(
        db, uid, password, MODEL, "create",
        [records]
    )
    print(f"[Load] Створено {len(new_ids)} записів у Odoo. ID: {new_ids}")
    return new_ids


# ==================================================
# VERIFY — перевірка результату
# ==================================================
def verify(ids):
    """Зчитує створені записи та виводить для перевірки."""
    if not ids:
        return

    results = models.execute_kw(
        db, uid, password, MODEL, "read",
        [ids],
        {"fields": ["name", "group_code", "avg_grade", "status", "is_honors"]}
    )

    print(f"\n{'ПІБ':<25} {'Група':<10} {'Бал':<8} {'Статус':<18} {'Відзнака'}")
    print("-" * 75)
    for s in results:
        honors = "✓" if s["is_honors"] else ""
        print(
            f"{s['name']:<25} {s['group_code']:<10} "
            f"{s['avg_grade']:<8.2f} {s['status']:<18} {honors}"
        )


# ==================================================
# Головний потік
# ==================================================
if __name__ == "__main__":
    filepath = sys.argv[1] if len(sys.argv) > 1 else CSV_FILE

    rows = extract(filepath)
    records = transform(rows)
    new_ids = load(records)
    verify(new_ids)
```

### 7.4. Захист від дублікатів

У реальних ETL-процесах часто потрібно перевіряти, чи запис вже існує в системі. Додайте до функції `load` перевірку за ім'ям та групою:

```python
def load_with_dedup(records):
    """Створює записи, пропускаючи ті, що вже існують (за name + group_code)."""
    created_ids = []
    skipped = 0

    for rec in records:
        existing = models.execute_kw(
            db, uid, password, MODEL, "search",
            [[("name", "=", rec["name"]), ("group_code", "=", rec["group_code"])]]
        )
        if existing:
            print(f"  Пропущено (дублікат): {rec['name']} ({rec['group_code']})")
            skipped += 1
        else:
            new_id = models.execute_kw(
                db, uid, password, MODEL, "create", [rec]
            )
            created_ids.append(new_id)

    print(f"[Load] Створено: {len(created_ids)}, пропущено: {skipped}")
    return created_ids
```

> **Компроміс продуктивності.** Поштучна перевірка дублікатів генерує N+1 HTTP-запит (N search + N create). Для великих обсягів (тисячі записів) ефективніше завантажити всі існуючі записи одним `search_read`, побудувати множину ключів у пам'яті і фільтрувати локально. У цій роботі обсяги невеликі, тому поштучний підхід є прийнятним та наочнішим.

# ЧАСТИНА III. АВТОМАТИЗАЦІЯ ВСЕРЕДИНІ ODOO

## 8. Серверна дія (Server Action)

Серверні дії дозволяють виконувати Python-код безпосередньо в середовищі Odoo, з доступом до ORM, без зовнішнього скрипта.

### 8.1. Створення серверної дії через інтерфейс

1. Увійдіть в Odoo як адміністратор. Переконайтеся, що режим розробника активовано.
2. Перейдіть у **Settings → Technical → Server Actions**.
3. Натисніть **New** та заповніть:
   - **Action Name:** Оновити статус відмінників
   - **Model:** edu.student
   - **Action To Do:** Execute Python Code
   - **Python Code:**

```python
# Знаходимо студентів зі статусом 'studying' та балом >= 90
students = env["edu.student"].search([
    ("status", "=", "studying"),
    ("avg_grade", ">=", 90),
])

# Логуємо знайдених
log(f"Знайдено {len(students)} відмінників для оновлення")

# Для демонстрації: додаємо до імені позначку (у реальному сценарії
# тут може бути зміна статусу, відправка листа тощо)
for student in students:
    if "★" not in student.name:
        student.name = f"{student.name} ★"
        log(f"  Оновлено: {student.name}")
```

4. Натисніть **Save**, потім **Run** (кнопка ▶ у верхній панелі).
5. Перевірте результат: перейдіть до **Education → Студенти** і переконайтеся, що в іменах відмінників з'явилася зірочка.

### 8.2. Аналіз серверної дії

Зверніть увагу на контекст виконання серверної дії:
- `env` — середовище Odoo (аналог `self.env` у коді моделі);
- `model` — поточна модель (`edu.student`);
- `log(message)` — запис у лог серверної дії (видно на вкладці Logs після виконання);
- `records` — набір записів, якщо дія прив'язана до конкретних записів (у нашому випадку — порожній, бо ми запускаємо вручну на всій моделі).

Серверні дії виконуються в одній транзакції: якщо на будь-якому записі виникне помилка, всі зміни скасовуються (rollback).

## 9. Запланована дія (Scheduled Action / Cron)

### 9.1. Створення запланованої дії

1. Перейдіть у **Settings → Technical → Scheduled Actions**.
2. Натисніть **New** та заповніть:
   - **Action Name:** Автоматичний перерахунок статусу студентів
   - **Model:** edu.student
   - **Execute Every:** 1 Days
   - **Next Execution Date:** оберіть сьогоднішню дату
   - **Number of Calls:** -1 (необмежено)
   - **Python Code:**

```python
# Запланована дія: перевіряє бал кожного студента
# і коригує статус, якщо бал нижчий за прохідний

PASSING_GRADE = 60.0

at_risk = model.search([
    ("status", "=", "studying"),
    ("avg_grade", "<", PASSING_GRADE),
    ("avg_grade", ">", 0),
])

log(f"Знайдено {len(at_risk)} студентів з балом нижче {PASSING_GRADE}")

for student in at_risk:
    log(f"  УВАГА: {student.name} ({student.group_code}) — бал {student.avg_grade}")
```

3. Натисніть **Save**.
4. Для тестування натисніть **Run Manually** (без очікування розкладу).

### 9.2. Перевірка виконання

Після запуску перевірте результат на вкладці **Logs** запланованої дії або у логах контейнера:

```bash
docker logs --tail 30 odoo19-app | grep "Знайдено"
```

> **Для продуктивних систем.** У реальному ERP заплановані дії використовуються для: щоденного перерахунку залишків на складі, автоматичного нагадування про прострочені рахунки, синхронізації даних із зовнішніми системами за розкладом, формування щоденних звітів. Принцип той самий — Python-код, що виконується за розкладом `ir.cron`.
